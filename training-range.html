Cyber training range

A private practice range for the offensive cyber operations course I instruct, built so every student can run the full attack chain on their own laptop as often as they want.

Runs on
Docker on each student's Windows, Mac or Linux laptop
Built for
A class of 40, one isolated range per student
Covers
Recon, pivoting, credential attacks, privilege escalation, packet analysis

Why I built it

The course ends in a practical evaluation, and the skills it tests only stick with repetition: scanning through a proxy, building tunnels, spraying credentials, moving files, escalating privileges and reading packet captures. I wanted every student to have that whole chain on their own machine, on their own schedule, without needing an instructor or shared infrastructure to practice.

What a student gets

  • A real Kali desktop in the browser. One double-click starts the lab and opens Kali in a browser tab. A lighter terminal-only mode covers laptops that struggle with the desktop.
  • A small network to work through. A jumphost, a router and three targets, each built around a different technique, with eight objectives that run in the same order as the evaluation.
  • A guide that teaches, not just directs. The student guide gives hints rather than answers and explains why each step works, so students understand the technique instead of copying commands.
  • Unlimited reps. A reset rebuilds every target with new flags and new passwords. Students' notes live outside the lab, so they survive resets and updates.

Forcing the pivot

The topology does the teaching. Kali sits on an edge network, the targets sit on an internal network, and only the jumphost is on both. There is no shortcut around the tunnel, so a student who reaches a target has actually built and used one. The internal network has no route to the internet, so nothing deliberately vulnerable can reach out, and the browser ports are bound to the student's own machine.

No answer key to leak

Flags and passwords are generated randomly on each laptop at first start and again on every reset. Students check flags with a small local script that compares against their own machine's values and tracks progress, with no server involved. Because every student's lab is different, a flag shared in a group chat is worthless to anyone else.

Built for 40 laptops, not one

A lot of the engineering went into making setup survive whatever hardware students bring.

  • A preflight check that tests, not assumes. It runs each dependency and checks the result. On Windows that matters: WSL's command always exists, and a placeholder Python opens the Microsoft Store instead of running.
  • Double-click launchers on Windows. Small wrappers run the PowerShell scripts without students touching execution policy, and stay open so errors are readable.
  • Defensive defaults. Line endings are forced so Windows checkouts don't break the Linux containers, and a fixed project name means a second download manages the same lab instead of colliding with it.
  • Troubleshooting by error message. The README maps each error students are likely to see, word for word, to an exact fix.

Tested like production

Kali and Debian are rolling releases, so a lab that builds today can break next week. Continuous integration builds every image from a clean checkout on each change, boots Kali the way a student would, stands up the real topology and asserts the isolation rules still hold: Kali can't reach the internal network, and the targets can't reach the internet. That test caught a subtle bug, where Docker quietly reserves the first address of each subnet for itself and collided with the router's address from the course material.

The base images are pinned to exact digests, so every student and the CI pipeline build an identical environment, and security updates arrive as a deliberate, reviewable change instead of silent drift.

Why it matters

I'm passionate about developing the people around me, and this is what that looks like in practice: removing every barrier between a student and the reps they need. The same instincts carry over to my security work. Isolate what's dangerous, generate secrets instead of sharing them, and test the guarantees you depend on rather than assuming them.
