Deploying the lab with Terraform

One Terraform file stands up the whole security lab: network, instances, logging and the permissions between them.

Provisions
VPC, subnet, routing, 3 EC2 instances, S3 log bucket
Access control
Security groups pinned to the operator's IP, scoped IAM role
Source
main.tf on GitHub

Why Infrastructure as Code

A lab you build by hand drifts. Security group rules get loosened to debug something and never get tightened again. Defining the lab in Terraform keeps it reviewable and repeatable, and I can destroy it when I'm not using it, which keeps the attack surface and the bill at zero.

What it builds

  • A VPC (10.0.0.0/16) with a public subnet, internet gateway and route table.
  • Three EC2 instances: the target web server, the Nessus scanner and the attack platform, each with its own security group.
  • A private S3 bucket for logs, named with a random suffix so every deployment is unique.
  • An IAM role and instance profile that let only the web server write to that bucket.

Locking access to the operator

Rather than hard-coding an IP, the script looks up the public address of whoever runs terraform apply and allows SSH from that single /32. The Nessus UI on port 8834 gets the same treatment. Only the target's HTTP port is open to the internet, because that's the thing being attacked.

A logging role that can't do anything else

The web server needs to push logs to S3, so it gets an instance role instead of stored access keys. The policy names the one bucket it can touch and nothing more.

What I'd tighten next

Reading the script with my day-job eyes, these are the changes I'd make before calling it production-grade:

  • Require IMDSv2 on every instance with metadata_options { http_tokens = "required" }, which blunts SSRF-style credential theft from the vulnerable web app.
  • Add an S3 public access block and replace the legacy bucket ACL with Object Ownership settings.
  • Drop s3:GetObject from the logging role, since the server only ever writes.
  • Pin the AWS and HTTP provider versions, and look up AMIs with a data source instead of placeholders.
