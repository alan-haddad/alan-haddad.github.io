Deploying the lab with Terraform

One Terraform file stands up the whole security lab: network, instances, logging and the permissions between them.

Provisions
VPC, subnet, routing, 3 EC2 instances, S3 log bucket
Access control
Security groups pinned to the operator's IP, write-only IAM role
Source
main.tf on GitHub

Why Infrastructure as Code

A lab you build by hand drifts. Security group rules get loosened to debug something and never get tightened again. Defining the lab in Terraform keeps it reviewable and repeatable, and I can destroy it when I'm not using it, which keeps the attack surface and the bill at zero.

What it builds

  • A VPC (10.0.0.0/16) with a public subnet, internet gateway and route table.
  • Three EC2 instances: the target web server, the Nessus scanner and the attack platform, each with its own security group.
  • A private S3 bucket for logs, named with a random suffix so every deployment is unique.
  • An IAM role and instance profile that let only the web server write to that bucket.

Locking access to the operator

Rather than hard-coding an IP, the script looks up the public address of whoever runs terraform apply and allows SSH from that single /32. The Nessus UI on port 8834 gets the same treatment. The target is deliberately vulnerable, so it is never open to the internet: only the operator, the scanner and the attack platform can reach it.

A logging role that can't do anything else

The web server needs to push logs to S3, so it gets an instance role instead of stored access keys. The policy names the one bucket it can touch, and it can write and list but never read a log back.

Hardening the defaults

The first version of this script worked, but it leaned on defaults I wouldn't accept at work. These are the changes I made:

  • Every instance requires IMDSv2 with metadata_options { http_tokens = "required" }, which blunts SSRF-style credential theft from the vulnerable web app.
  • The log bucket has a public access block, bucket-owner-enforced ownership in place of the legacy ACL, default encryption, and a policy that refuses requests without TLS.
  • The logging role lost s3:GetObject, since the server only ever writes.
  • Provider versions are pinned, and the AMI comes from a data source instead of a placeholder.
  • Root volumes are encrypted, and a GitHub Actions check runs terraform fmt and terraform validate on every change.

What I'd tighten next

  • Move the scanner and the target into a private subnet, and reach them through Systems Manager Session Manager instead of SSH.
  • Turn on VPC Flow Logs, so the lab's network traffic lands in the SIEM alongside the web logs.
